- A table that takes a name by RESTORE TABLE, SWAP TABLES or ALTER TABLE ... RENAME TO no longer accepts an `IF VERSION` write with a version read from a table that held the name before: after `RESTORE TABLE world FROM ... AS world_restored` and `SWAP TABLES world, world_restored`, or a RESTORE TABLE or RENAME TO onto the name of a dropped table, a chunk could carry or reach a version a client had read under the name, with other data, and the stale write applied. SWAP TABLES and RENAME TO raise the data directory's `version_floor` above the clocks of their tables, as DROP TABLE does, and the table that takes the name records it as its name floor (table manifest option 15), synced before the name changes; its chunks written before report the name floor as their version in GET BLOCK, GET CHUNK, GET AREA, SCAN CHUNKS, SET and DELETE replies, RETURNING, VERSION_MISMATCH and CONDITION_FAILED and in every IF VERSION check, its clock opens above the floor, and a writer opens every table clock at or above `version_floor`. A client re-reads such a chunk once to get a matching version. Revisions used as positions keep their stored values, and a watch at the fork revision of a restored table still continues after SWAP TABLES. A build without option 15 refuses such a table (#306).

  Read the ops_s column with care: as writers are added the eviction pass overshoots
  (evictions per write climbs from 1.02 to 2.09) and the cache ends nearly empty at
  32-64 writers (loaded_chunks 300 and 2). Part of the throughput gain is therefore a
  smaller resident set, not only bracket sharing. ms_per_eviction stays the fair
  comparison; it falls ~68x from 1 to 32 writers.

    5983, 5965, 5982, 5981, 5965, 5982, 5966
    mean = 5975 B per resident chunk (stddev 9) for 544 B of chunk state
    -> max_loaded_chunks=16384 costs about 93 MiB of RSS
  Later repeats inside the same process report lower values because they reuse heap
  freed by the previous repeat's evictions; use the first-repeat figures above.
  Switching from ru_maxrss to current RSS did NOT lower this number: the historical
  "~5.6 KiB per resident chunk" is confirmed, not a peak-measurement artifact.

=== cross-check against the historical mixed average ===
  ./build-bench/chunkdb_bench --ops 20000 on the same host and session:
    sparse_world_writes ops_s=358.69 total_s=55.7588
    sparse_metrics evictions=5125 ... evictions_per_op=0.2562
    hot_chunk_writes ops_s=47340.90
  55.7588 s / 5125 evictions = 10.88 ms per eviction, i.e. the same physical cost as the
  11.75 ms measured in steady state. The historical "~355 sparse ops/s" figure therefore
  reproduces exactly (358.69); it was never in conflict with the "58-115 ops/s" steady-state
  figure - only 25.6% of its operations evict.

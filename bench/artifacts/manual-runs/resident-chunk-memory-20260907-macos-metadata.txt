which column to read:
  rss_bytes_per_warm_chunk is the memory figure: it is taken at the end of the
  warm-up, when the cache holds exactly max_loaded_chunks chunks and no
  eviction has run. rss_bytes_per_resident_chunk is taken at the end of the
  measured window and additionally contains heap that eviction freed but the
  allocator has not returned to the OS. Both are reported below.
  Use the FIRST repeat of each process for either: from the second repeat
  onward the warm-up is satisfied out of heap freed by the previous repeat, so
  the RSS delta understates the cost.

what this run does NOT measure:
  - throughput conclusions. Both runs report ms_per_eviction for sanity, but
    they were taken while one other benchmark process had the machine's
    benchmark lock queued behind them and are not a throughput comparison; the
    change touches memory, not the eviction path's syscalls.
  - Linux, Windows, durability modes other than relaxed: unchanged from the
    2026-09-05 artifact, still not measured.

companion evidence: resident-chunk-memory-20260907-macos-heap-attribution.txt
records the same before/after warm-up under a counting global operator
new/delete, which names every live allocation class per resident chunk and is
what makes the RSS delta attributable rather than merely observed.

durable sync actually taken on this filesystem: fullfsync
  The benchmark probes fcntl(fd, F_FULLFSYNC) on the data directory before the
  run and reports whether it succeeded or fell back. This matters because
  src/durability_io.cpp:288-301 falls back to plain fsync when F_FULLFSYNC
  returns EINVAL/ENOTSUP/ENOTTY, and a run that silently took the fallback is
  not comparable with one that did not. This run reports `durable_sync=fullfsync`
  (no fallback); the probe's median is recorded per row in the CSV files.

methodology (what differs from the ad-hoc harnesses of 2026-09-03):
  - the warm-up phase writes exactly max_loaded_chunks fresh chunks and is NOT
    part of the measured window. Those writes cost no eviction, and mixing them
    into the average is what produced the several non-comparable sparse
    throughput figures previously quoted in docs/.
  - every repeat runs on a fresh data directory and a fresh store.
  - RSS is the CURRENT resident size (mach_task_basic_info on macOS,
    /proc/self/statm on Linux), not getrusage(ru_maxrss). ru_maxrss is a
    high-water mark and was the measurement used for the historical
    "~5.6 KiB per resident chunk" figure.
    rss_bytes_per_warm_chunk is measured at the end of the warm-up, when the
    cache is exactly full and no eviction has run yet; rss_bytes_per_resident_chunk
    is measured at the end of the measured window, after eviction churn.
  - store teardown is excluded (the benchmark does not close the store unless
    --close-store is passed): closing flushes every resident dirty chunk and
    costs O(max_loaded_chunks) snapshot-generation brackets, which is the same
    per-eviction cost already reported, paid again at a fixed multiple.
  - the reported RSS baseline is taken per repeat immediately before the store
    is created, so a leaked previous store shifts the baseline but not the delta.
    Caveat: from the second repeat onward the allocator can satisfy the warm-up
    out of heap freed by the previous repeat's evictions, which understates the
    delta. Use the FIRST repeat of each process for the per-resident-chunk
    figure; the summary file lists those seven values explicitly. At 32 and 64
    writers the eviction pass also overshoots badly (the cache ends holding a
    couple of chunks), which makes `rss_bytes_per_resident_chunk` meaningless in
    those rows - `rss_bytes_per_warm_chunk` is the column to read.

not covered by this snapshot:
  - Linux/ext4 (or any platform where the durable sync is fdatasync rather than
    F_FULLFSYNC) has NOT been measured. Absolute numbers there are expected to
    differ substantially, and the writer-scaling shape may differ too. Until a
    second host is measured, treat every figure here as macOS/APFS-specific.
  - Windows has not been measured with this benchmark.
  - durability modes other than `relaxed` have not been measured with this
    benchmark.

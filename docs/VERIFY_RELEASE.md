# Verify Release Artifacts

This document explains what the `.sha256` sidecar files are for and how to verify downloaded `chunkdb` release artifacts.

## What The `.sha256` Files Are For

Each packaged release archive is accompanied by a `.sha256` file.

The `.sha256` file lets you compare:

- the expected SHA256 hash recorded at release time
- the actual SHA256 hash of the file you downloaded

This is an integrity check.
It helps detect download corruption or accidental file mismatch.

It is not the same as:

- cryptographic signing
- maintainer identity verification
- a full supply-chain trust model

## Packaged Binaries vs GitHub Source Archives

`chunkdb` releases contain two different artifact types:

- packaged release archives uploaded by the maintainer
- GitHub auto-generated source archives

Packaged release archives:

- look like `chunkdb-<version>-<platform>.tar.gz` or `chunkdb-<version>-<platform>.zip`
- contain the packaged release payload produced by CPack
- have matching `.sha256` sidecar files

GitHub auto-generated source archives:

- appear as `Source code (zip)` and `Source code (tar.gz)`
- are generated by GitHub from the tag
- are source snapshots, not compiled binary packages
- should not be confused with the packaged release archives

## Important Note About The Current `.sha256` Files

The current `.sha256` sidecar files contain the release-time filename entry exactly as generated during packaging.

That means the most portable verification method is:

1. compute the hash of the downloaded file
2. read the first field from the `.sha256` file
3. compare the two values

## macOS

Compute the downloaded artifact hash:

```bash
shasum -a 256 chunkdb-0.1.1-Darwin-arm64.tar.gz
```

Read the expected hash from the sidecar:

```bash
awk '{print $1}' chunkdb-0.1.1-Darwin-arm64.tar.gz.sha256
```

One-line comparison:

```bash
test "$(shasum -a 256 chunkdb-0.1.1-Darwin-arm64.tar.gz | awk '{print $1}')" = "$(awk '{print $1}' chunkdb-0.1.1-Darwin-arm64.tar.gz.sha256)" && echo OK || echo MISMATCH
```

## Linux

Compute the downloaded artifact hash:

```bash
sha256sum chunkdb-0.1.1-Darwin-arm64.tar.gz
```

Read the expected hash from the sidecar:

```bash
awk '{print $1}' chunkdb-0.1.1-Darwin-arm64.tar.gz.sha256
```

One-line comparison:

```bash
test "$(sha256sum chunkdb-0.1.1-Darwin-arm64.tar.gz | awk '{print $1}')" = "$(awk '{print $1}' chunkdb-0.1.1-Darwin-arm64.tar.gz.sha256)" && echo OK || echo MISMATCH
```

## Windows PowerShell

Compute the downloaded artifact hash and compare it to the `.sha256` sidecar:

```powershell
$actual = (Get-FileHash .\chunkdb-0.1.1-Darwin-arm64.zip -Algorithm SHA256).Hash.ToLower()
$expected = (Get-Content .\chunkdb-0.1.1-Darwin-arm64.zip.sha256).Split()[0].ToLower()
if ($actual -eq $expected) { "OK" } else { "MISMATCH" }
```

If you prefer `certutil` for manual inspection:

```powershell
certutil -hashfile .\chunkdb-0.1.1-Darwin-arm64.zip SHA256
Get-Content .\chunkdb-0.1.1-Darwin-arm64.zip.sha256
```

## What Verification Does And Does Not Mean

If the hashes match:

- you downloaded the same bytes that were attached to the release

If the hashes do not match:

- the download is corrupted, incomplete, or not the same file as the published artifact

Even when the hashes match, this does not by itself prove:

- who built the artifact
- that the machine was trusted
- that the artifact is signed

Checksum verification is an integrity check, not a full trust/signing system.
